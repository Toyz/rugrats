# Docs

`docs/` is the reference manual for Rugrats: Search for Reptar on the PlayStation:
what the formats are, how the engine works, what is on the disc. It is written
for someone who wants to write a parser or a subsystem and does not care how we
found out.

The worklog (see the `worklog` skill) is the other half. Worklog says *how we
found out* and *why*; docs says *what is true*, flatly, in its final form. When
a worklog entry establishes a format, the same session writes or updates the
docs page for it. A format is not documented until both exist.

## Layout

```
docs/README.md                index - generated by `rugrats-re docs index`
docs/disc/layout.md           the CD: tracks, file system, boot, what sits where
docs/formats/<name>.md        one page per container or record format
docs/engine/<name>.md         one page per subsystem
docs/engine/memory-map.md
docs/content/inventory.md     what is on the disc, with counts
docs/cut/<name>.md            one page per cut, missing or unreachable thing
```

Filenames are lower-case, hyphenated, and named after the thing, not the
session: `file-table.md`, not `track-notes-2.md`.

The sections are fixed in `crates/rugrats-re/src/docs.rs` (`SECTIONS`). A page in
a folder that is not listed there does not reach the index; add the section
first.

## Every page starts with front matter

```markdown
---
title: The CD and its file system
status: solid | partial | guess
discs: US | all
covers: US SYSTEM.CNF, US SLUS_006.50:0x80012345
worklog: 1, 3
---
```

`status` is the honesty knob and it is the most important field on the page:

| status | means |
| --- | --- |
| `solid` | round-trips, or every field is accounted for across every sample |
| `partial` | parses, but named fields remain unknown or unverified |
| `guess` | a hypothesis written down so the next session can attack it |

Downgrade a page the moment a sample breaks it. A `solid` page that is wrong
costs more than no page.

`discs` says which releases the page has been checked against, by tag: `US`
(SLUS-00650, the only disc in `original/` today), `EU` (the PAL release, if one
is ever added), or `all`. `status` is a claim about the listed discs and no
others.

`covers` names what the page describes, with the same locators the worklog
uses: disc paths, archive members after `::`, and addresses in the executable
(`SLUS_006.50:0x8001xxxx`, KSEG0 RAM addresses as the code sees them) or in an
overlay (`OVERLAY.BIN:0x80xxxxxx`).

`worklog` lists the entry numbers that established the page, comma separated,
so the reference points back at the evidence.

## A format page

Lead with the layout. A reader should be able to write the parser from the first
screen and read the prose only when something surprises them.

````markdown
# The FOO.DAT archive

One sentence saying what it is and where it is used.

## Layout

All little-endian (the R3000A is little-endian). Offsets are from the start of
the file.

```
header
  u32       count               number of entries
  entry[count]
    u32     offset              from the start of the file
    u32     size                bytes
```

## Fields

`offset` - ... what is known about each field that the table cannot say.

## Notes

Quirks, engine behaviour that depends on the layout, and things a
re-implementation must preserve bug-for-bug.

## Unknown

A list, or "nothing". Never leave this section out - an empty one is a claim,
and a missing one is a silence.
````

Give a worked example when the layout is at all subtle: a real hexdump from a
real entry with the fields labelled. Use a file that is actually on the disc and
name it, so the example can be re-checked.

## An engine page

Lead with what the subsystem does and the entry points: the function addresses,
the globals it owns, the overlay it lives in. Then the data flow. Name functions
by what they do, and give the address every time; the executable carries no
symbols we can trust until a page says otherwise.

## A cut page

Anything the game names, references or half-carries but does not ship whole
gets its own page under `docs/cut/`, so cut content is tracked in one place
rather than buried in the `Unknown` list of whichever page found it: a track
named in the text with no archive, a mode with strings but no reachable menu,
an asset no code loads, a function nothing calls. Lead with what exists and
where (the locators), then what is missing, then whether the code can still
reach it. The page that found it links to the cut page instead of repeating
it. When a cut item is restored in the port, the page says so and how.

## Rules

- No emojis.
- Exact constants. Offsets in hex, sizes in decimal, and say the endianness once
  at the top of the layout block.
- Every structure field gets a type and a name, even when the name is
  `unknown_0c`. Numbered unknowns beat leaving a gap in the table.
- Distinguish measured from inferred. "All 412 files have this" is a
  measurement; say the sample size. "This is probably a flag word" is inferred;
  say so.
- Never write aspirational documentation. Docs describe what has been observed
  in the data or in the binary, not what a tool or the port intends to do.
- One thing per page. If a page grows two subjects, split it.
- Cross-link with relative paths: `[the overlay header](overlay.md)`.
- Run `cargo run -q -p rugrats-re -- docs check` before finishing: it catches
  missing front matter, an unknown status or disc tag, a stale index, and a dead
  relative link. `docs index` regenerates `docs/README.md`.
